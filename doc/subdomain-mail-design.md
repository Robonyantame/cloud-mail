# 子域名邮箱功能设计

状态：已确认（2026-09-14），配置方式于 2026-09-15 按用户要求调整。功能已实现并通过本地行为测试；实际收信及容量尚未验证。

## 已确认需求

- 为不同网站提供独立收信地址，首要入口为批量 API。
- 基础域名复用既有 `domain` 列表，`subdomain_domains` 保存随机生成或管理员指定的子域标签；每个标签应用于所有基础域名，不再需要 `subdomain_base`。
- 新地址归属于同一已有用户，不为每个网站创建独立登录用户。
- 首版批量 API 仅供管理员脚本使用。
- 按已创建的完整邮箱地址接收邮件，未创建的同子域地址不作为该用户邮箱接收。
- 地址长期有效，支持独立查询和主动停用；停用地址不得分配给别人。
- 子域配置与邮箱创建分开：添加子域时支持随机或自定义子域标签；批量创建邮箱时复用选定的已接入子域，不为每个新地址生成新子域。
- 首版由管理员在 Cloudflare 预先配置子域，通过实际收信验证后启用；项目不自动配置 Cloudflare。
- 批量 API 支持指定前缀列表，或仅指定数量以生成随机前缀；自定义前缀冲突时明确报告，不自动改名。
- 单次批量最多 100 个，逐项返回结果，部分失败不回滚已成功创建的邮箱。
- 支持请求标识，同一请求重试返回原结果，避免重复生成地址。
- 默认给管理员本人创建；允许指定已有用户，遵守目标用户的邮箱数量限制和域名权限。
- 停用后拒收新邮件，旧邮件仍可查询并遵循现有邮件清理设置；原用户可以恢复使用。
- 未创建的完整地址拒收，包含未创建的 `+tag` 地址。
- 配置文件维护可用子域，API 提供批量创建、列表、停用、恢复，现有页面查看邮件。2026-09-15 补充管理员网页创建入口：在用户列表中给所选已有用户添加子域邮箱，不创建独立登录用户。
- 辅助命令生成随机子域名称，管理员完成 Cloudflare 配置并实际收信验证后将其加入可用列表。

## 已确认的细节规则

- 重试保证窗口为首次受理后 24 小时；同请求标识改参数报冲突，过期后不能依赖原请求标识防止重复创建。
- 停用地址仍占用户邮箱额度；永久删除或删除所属用户后，保留地址占用记录，防止未来重新分配。
- 新子域邮箱限定收信用途，不自动开放发信或公开注册；普通用户仍通过现有界面读取自己的邮件。
- 新 API 沿用全局新增邮箱开关、前缀限制、目标用户权限与额度；管理员令牌调用不要求浏览器人机验证。角色域名权限仍要求完整子域匹配。
- 新 API 增加按 accountId 精确查询邮件，避免现有开放接口 LIKE 筛选带来的通配歧义。
- 单层子域标签使用小写字母、数字及内部连字符，长度 1–63；随机子域标签默认 10 位小写字母数字。邮箱随机前缀默认 12 位小写字母数字，并适配已配置的最短长度及禁用词规则；自定义前缀沿用邮箱格式限制，统一大小写判重。
- 每日新增量和长期存量没有用户估计值，不声明已验证容量，不因本次设计擅自增加每日限额。实现后验证单次 100 个及并发批次的正确性。

## 配置和启用流程

1. 管理员自定义一个子域标签，或运行辅助命令生成候选名称，例如 `shop.example.com`。命令只生成名称，不修改 DNS 或 Cloudflare 账户。
2. 在 Cloudflare 启用该子域的 Email Routing，完成 DNS 和发往本项目 Worker 的路由配置。
3. 用测试部署、临时探针邮箱完成外部真实发信验证；该探针必须是已创建的完整地址。DNS 存在或 API 创建成功都不等同于收信验证通过。
4. 在 `domain` 中维护基础域名，在 `subdomain_domains` 中维护标签；部署后展开为全部「标签.基础域名」组合。新增任一标签或基础域名前，管理员须完成相应新增组合的实际收信验证，首版没有自动检测和认证流程。
5. API 仅在展开后的启用子域创建地址，调用仍指定完整子域；非管理员目标用户还须具有该完整子域的权限。

例如 `domain = ["mxr.cc.cd", "roop.cc.cd", "tame.cc.cd"]`、`subdomain_domains = ["shop", "tools"]` 会启用六个完整子域，包含 `shop.mxr.cc.cd` 和 `tools.tame.cc.cd`。标签列表不接受完整域名。配置变更不修改既有地址、归属和请求结果。

基础域名的授权不自动包含任意子域。子域标签单独配置，展开后的完整子域不加入公开注册/普通创建列表。移除标签会停用它在全部基础域名下的组合，移除基础域名会停用其下全部组合；停止新建及接收，但保留既有地址、归属和历史邮件。持久化保留已管理完整子域及地址的标记，整个子域都不能退回旧版宽松收信逻辑。

随机生成子域与随机生成邮箱前缀是两个独立步骤。批量 API 不临时创建 DNS、不从所有子域中随机选一个，也不把不存在的随机子域伪装为可用。

## API 契约

以下 Public API 使用现有管理员 Authorization 令牌。userId 可省略，默认管理员；不能创建不存在的用户。沿用项目响应结构 `{code, message, data}`。

网页管理员入口为“用户列表 → 操作 → 邮箱 → 添加子域邮箱”，支持指定前缀和随机生成，复用同一批量创建服务。网页使用管理员现有登录 JWT 调用 `/user/subdomainMailbox/domains` 与 `/user/subdomainMailbox/batchCreate`，后台按管理员数据库身份校验；不在网页保存或获取全局 Public API 令牌，也不开放普通用户注册子域账号。网络中断或处理中时保存原请求重试，超过 24 小时须先核对已有地址。

### 创建邮箱

`POST /public/subdomainMailbox/batchCreate`

每次指定一个完整子域和一个归属用户。随机模式与自定义模式互斥：count 或 prefixes 必须且只能提供一个；数量为 1–100。requestId 为必填、不超过 128 字符的调用方唯一标识。

随机模式示例：

```json
{
  "requestId": "website-addresses-20260914-001",
  "domain": "shop.example.com",
  "count": 2
}
```

自定义模式示例（userId 为示例，调用方须替换为真实已有用户）：

```json
{
  "requestId": "website-addresses-20260914-002",
  "domain": "shop.example.com",
  "userId": 42,
  "prefixes": ["github", "shopping"]
}
```

部分成功的响应示例：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "requestId": "website-addresses-20260914-002",
    "created": 1,
    "failed": 1,
    "items": [
      {"index": 0, "email": "github@shop.example.com", "accountId": 123, "status": "created"},
      {"index": 1, "email": "shopping@shop.example.com", "status": "failed", "error": "ADDRESS_UNAVAILABLE"}
    ]
  }
}
```

- items 保持输入顺序。自定义地址冲突、已退役地址、非法前缀和额度不足逐项报错；随机冲突有限重试后报明确生成失败，不无限循环。
- 鉴权失败、归属用户无效、域名不可用、模式冲突或数量超限等请求级错误不创建任何地址。
- 同一批次内自定义前缀也判重。用户额度不足时按输入顺序尽可能创建，其余返回额度不足。
- 同一 requestId 和相同规范化参数在 24 小时内重试，返回首次记录的逐项结果，包括失败项；若只想重试失败项，使用新的 requestId。
- 同一 requestId 在保证窗口内变更参数返回冲突。正在处理的相同请求返回处理中及重试提示，不启动第二批创建。
- 请求标识以新 API 操作及管理员身份为范围；令牌轮换不改变管理员身份。首次解析出的目标用户和参数一并保存。
- 中断后仍须保存已经成功创建的地址及其请求归属，重试不能重复创建。并发批次也不能超出角色配额；这两点是实现要求，不能仅通过客户端约定保证。
- 24 小时以后重新提交同一标识可能被视为新请求。脚本应保留已返回结果，超过保证窗口先查询已创建地址再决定是否新建。

### 查询和状态管理

| 接口 | 主要参数 | 行为 |
| --- | --- | --- |
| `GET /public/subdomainMailbox/list` | userId、domain、status、cursor、size | 默认管理员本人；查询其地址，默认每页 20，最多 100；支持 active/disabled 状态筛选 |
| `POST /public/subdomainMailbox/disable` | accountId | 停用已有地址；重复调用成功，不删除历史邮件 |
| `POST /public/subdomainMailbox/enable` | accountId | 恢复原用户地址；要求域名可用、用户有效及仍有域名权限；重复调用成功 |
| `GET /public/subdomainMailbox/emails` | accountId、cursor、size | 按账号精确查询收件，默认每页 20，最多 50；停用地址仍可查历史邮件 |

列表使用稳定游标顺序。新查询接口仅针对本功能的邮箱；原有 `/public/addUser` 和 `/public/emailList` 保持现有接口语义。状态管理不允许通过修改 userId 转移邮箱归属，或把其他类型的邮箱当作本功能邮箱操作。

## 收信、停用与数据清理

- 邮箱记录仍归属于现有用户，由完整地址唯一标识，并持久化本功能管理标记。
- 对本功能子域，先检查域名是否启用，再对 SMTP 信封收件人作完整地址匹配，忽略大小写；地址和所属用户必须存在且可用。
- 未创建、停用、删除、无效用户、无域名权限的收件人拒收；不进入 `+tag` 回退或无主邮件保存逻辑。已显式创建的完整 `+tag` 地址可按同样规则接收。
- Cloudflare 入站与站内投递使用相同规则，不能从另一条投递路径绕过停用。
- 全局收信开关和现有过滤规则继续适用。其他旧域名继续沿用既有行为，不整体取消旧域名的 `+tag` 或无主收信配置。
- 停用是可逆状态，不是删除；它不改变邮箱归属，不释放占用名额，不删除邮件。
- 物理删除可沿用现有邮件和附件清理行为，但须独立保留地址占用记录。删除用户同样不得让其地址重新开放；被彻底删除的邮箱不承诺恢复。
- 邮件清理沿用 autoCleanDays；当前默认 0 表示关闭。autoCleanExclude 按用户主邮箱豁免其所有邮箱，不新增子域专用保留期限。长期有效的是地址，不代表每封邮件永久保存。
- 首版不承诺子域发信能力，并在发信入口明确拒绝使用本功能的地址作为发件地址；已有邮箱发信行为不变。

## 验收场景

1. 管理员按文档分别接入随机命名和自定义命名子域，在每个子域完成至少一次真实外部收信。
2. 在同一启用子域批量生成 100 个邮箱，地址唯一、归属正确，无新增 DNS 操作；101 个的请求整体拒绝。
3. 指定前缀列表时精确保留合法指定名称；非法、重名及退役地址逐项报错，其他项目成功。
4. 默认给管理员创建；指定已有普通用户时遵守该用户配额、完整域名权限和有效状态，不能因管理员代调用而绕过限制。
5. 模拟多个并发请求争用最后一个邮箱名额，至多创建一个；同一请求并发或中断重试不重复创建。
6. 24 小时内同标识同参数返回原结果；同标识改参数冲突；部分失败重试不隐式重做原失败项目。
7. 只创建 `alice@shop.example.com` 时，它可以收信，未创建的 `bob@shop.example.com` 和 `alice+tag@shop.example.com` 拒收，即使全局无主收件开启也如此。
8. 停用后外部及站内投递均拒收，旧邮件仍可读；恢复后继续收信，用户配额不因停用而释放。
9. 物理删除地址或所属用户后，清理行为符合现有设置，但同一完整地址不能分配给任何新用户。
10. 精确邮件查询不会把包含 `_` 或 `%` 的地址当作 LIKE 通配表达式，不返回其他 account 的邮件。
11. 子域移出可用列表后，原地址停止新建及收信，历史邮件保留，且不会回退旧收信规则。
12. 新子域不会出现在公开注册入口，发信入口不能以该类地址发送；原有普通邮箱的创建、收信、发信及清理行为没有意外变化。

实现验证分为自动化行为测试与实际 Cloudflare 收信验证。未完成外部投递验证时，只能报告代码检查通过，不宣称域名已能真实收信。

## 已调整的建议

- 初始建议为每个新邮箱分配一个新随机子域。用户在获知平台额度约束后，已确认改为复用选定子域，并支持随机或自定义命名子域。自定义名称同样占用域名额度。

## 已核实的环境事实

- 现有 `/public/addUser` 创建独立用户及其主邮箱，不是给已有用户添加邮箱。
- Public API 使用全站管理员令牌，现有邮件查询没有按用户限制范围。
- 现有域名配置和角色授权按完整域名匹配，基础域名不会自动授权其子域名。
- 入站优先按完整地址匹配，另有 `+tag` 回退和无收件人邮件策略；新功能的严格匹配需考虑这些现有行为。
- 2026-09-14 核对的 Cloudflare 官方说明：单 zone 的 Email Routing 和 Email Sending 合计最多配置 30 个域名，包含根域。官方子域接入流程要求启用子域并配置 DNS；尚未证实任意随机子域的通配入站支持。
